# Retrospective

Based on the current repository, the direction became clear: I wanted a professional home base that could represent me outside any one platform. Instead of only relying on LinkedIn, GitHub, or a resume link, I set out to build a portfolio that explains who I am, what kind of AI/ML work I am moving toward, and how someone can reach me.

What I actually built is a lightweight personal portfolio for K Praveen Kumar. The site introduces me as an ML Engineer Intern at FlyRank AI and a BTech Artificial Intelligence student at Marwadi University. It includes sections for About, Experience, Capabilities, Credentials, Find Me, and a Capstone / Featured Project area. I also added one real dynamic feature: a contact form powered by Netlify Forms. That matters because the site is not only a poster. A visitor can take action, send a message, and the submission can reach me through Netlify's backend.

The project changed during development from a simple personal-brand page into a more complete final submission package. The repository now includes documentation, a DNS walkthrough, a contact-form feature explainer, mobile audit notes, hardening review notes, demo materials, and final checklist files. Some earlier files point toward a Vercel/Supabase profile-agent idea, including `api/chat.js` and `supabase/schema.sql`, but the current visible production feature is the Netlify contact form. That distinction is important because the final package should describe what is really working, not what could work later.

One thing that did not work cleanly was trying to treat every assignment requirement as already complete. The project has strong evidence for mobile fixes, form hardening, and launch hygiene, but it does not yet have a complete V1/V2 evaluation dataset with real numbers. It also does not have a real demo video URL, a filled hours log, a published build-in-public post, analytics evidence, or a personal FlyRank badge verification URL. I chose to mark these gaps as TODO instead of turning them into fake achievements.

An important design decision was to keep the site plain and explainable. The project uses HTML, CSS, and a small amount of JavaScript rather than a heavy frontend framework. That choice fits the purpose of the site: it needs to be fast, readable, and easy for me to explain in a demo. The contact feature follows the same idea. Netlify Forms gives the site a backend without requiring me to maintain a custom server.

One important limitation is that browser validation is not the same as full server-side validation. The form blocks empty, invalid, and very short input in normal browsers, and it uses Netlify's honeypot field for spam reduction. However, a malicious client could still bypass frontend checks. If the site begins receiving spam or serious traffic, the next version should add stronger backend validation, rate limiting, or a serverless function.

What I would build next is a small public project write-up system inside the portfolio. The "Next Up" and Capstone sections already reserve space for proof of work. The next step would be to add one strong case study with a real problem, what I did, what changed, and what evidence is safe to publish. I would also complete the V1/V2 evaluation with a reproducible rubric instead of only descriptive audit notes.

The three most transferable things I learned were: first, documentation is part of the product, not something after the product. Second, honest limitations make a project more credible than polished exaggeration. Third, a simple working feature is more employable than several half-built ideas.

My way of working changed because I became more careful about evidence. Earlier, it was tempting to keep adding sections and polish. By the end, I was checking whether each claim had a file, a screenshot, a link, or a real test behind it. That shift from "make it look good" to "make it verifiable" is the main professional habit I want to carry forward.
